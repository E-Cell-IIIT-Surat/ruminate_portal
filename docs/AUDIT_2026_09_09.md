# Ruminate audit and UX pass — 9 September 2026

## Scope and evidence
This is a source audit with targeted fixes, not a certificate that every production workflow works.
Production records, real submissions, accounts, uploads and emails have not been modified.
A staging database and role-specific test accounts are needed for destructive and concurrency end-to-end tests.

## Architecture
Next.js App Router / React / TypeScript; shared public header and portal shells;
Zod validation; Auth.js Google and credentials with JWT sessions; Prisma PostgreSQL via pg adapter;
R2 signed private uploads; queued console/SMTP/Resend email; DB-backed notifications and audit history.
The API boundary uses lib/authz.ts and safeError. Domain rules live under lib/domain.
Prisma uses DATABASE_URL through a pool capped at five connections per process (10-second idle/connect timeouts).
DIRECT_URL is for Prisma migration tooling. No schema migration is introduced by this pass.

## Authentication and roles
PARTICIPANT owns applications and teams; REVIEWER and FACULTY_REVIEWER use assigned reviews;
PROGRAM_MANAGER has program-scoped grants; CONTENT_MANAGER has announcement:create;
SUPER_ADMIN has global permissions. The admin layout currently admits SUPER_ADMIN and PROGRAM_MANAGER only.
Public-team decisions currently require user:manage, not faculty review permissions.
JWT lifetime is 30 days. Deleting Session rows alone does not revoke JWTs.
Shared protected API entry now checks the active database account.
Automatic allowlist promotion now requires verified email ownership. Explicit database role assignments remain intact.
Google's authenticated email_verified signal establishes verification; manual signup does not.

## Remaining risks / decisions
1. Review existing SUPER_ADMIN assignments and audit history: the signup promotion fix does not silently revoke previously stored grants.
2. Global SSIP/workshop permissions versus program-scoped manager access need an explicit policy; do not silently remove existing staff access.
3. Legacy workshop booking accepts an unknown slug without a Workshop row and checks capacity outside its create transaction. Requires reconciliation of legacy booking flow and staging tests.
4. Email delivery has no claim/lease across simultaneous processors; overlapping cron/immediate sends may duplicate messages. SMTP cannot guarantee exactly-once delivery.
5. Status transitions read state before their transaction; competing decisions require a dedicated transactional regression pass.
6. Public program database failures become empty arrays, which can misrepresent an outage as no programs.
7. Generic Office upload signature checking recognizes ZIP signatures, not full OOXML structure; no malware scanning is configured.
8. Faculty team approval and CONTENT_MANAGER admin navigation differ from earlier desired capabilities. Role policy needs confirmation.
9. Feedback admin listing and SSIP data screens must be verified against the deployed migration state, not inferred from a successful compile.
10. No Playwright end-to-end suite existed. Domain tests do not establish all CRUD, role, delivery or responsive workflows.
11. Session expiry destination handling, all mobile widths, export volume limits, email-domain verification and error-log redaction need further coverage.

## Phase 2 continuation — 9 September 2026
- Workshop booking capacity is now checked inside a transaction protected by a workshop advisory lock. Unknown slugs are rejected except the intentionally preserved legacy `financial-literacy` mapping. The existing unique `(workshop,email)` constraint prevents duplicate registration.
- Email deliveries now use `PROCESSING`, `claimedAt`, `claimedBy`, and `nextAttemptAt`. A conditional update is the worker claim; stale processing claims can recover after two minutes; failures retry at bounded exponential intervals and stop after five attempts. SMTP still cannot guarantee exactly-once delivery after a network timeout.
- Public program database failures now raise `PublicDataError` and render an explicit retry state. Sitemap still degrades to static pages because crawlers should receive a valid response when the optional program query is unavailable.
- Office uploads now require the ZIP/OOXML package markers appropriate to DOCX, PPTX, or XLSX in addition to MIME, size, key, metadata and magic-byte checks. No malware scanner is available; files remain private and are never executed.
- New migration: `prisma/migrations/20260909000000_email_claims/migration.sql`. Apply it only to the intended staging/production database after review; do not run it automatically here.
- Final phase checks: `npm run db:generate`, `npm run typecheck`, `npm run lint`, `npm test` (18 passing tests), and `npm run build` all passed after these changes.

### Deployment handoff and remaining decisions
- The email-claim migration is intentionally present but unapplied. Before deploying the worker changes, run `npm run db:deploy` against the intended staging database first, verify the migration, then deploy the application. Do not apply it to an unknown or production database without a backup/rollback decision.
- No new environment variable names were introduced in this phase. Existing production values for authentication, database, R2, and email providers remain required; SMTP values are required only when `EMAIL_PROVIDER=smtp`.
- A real staging environment is still needed to verify Google OAuth, SMTP delivery, role-specific access, file uploads, booking capacity races, status transitions, and mobile layouts without touching live users or sending real mail.
- Dependency review is not fully clean: the non-forced audit fix removed critical findings, but transitive high/moderate advisories remain (notably Prisma/deepmerge-ts, nodemailer, and postcss). Do not use `npm audit fix --force` without reviewing major-version impact.
- The OOXML check is a package-marker hardening layer, not malware scanning. Add an external malware scanner before accepting untrusted documents at larger scale.
